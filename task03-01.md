## Alur Pengamanan Autentikasi

### 1. Penyimpanan Password (Registrasi / Seeding)

```
password plain-text → bcrypt → hashed_password (disimpan di DB)
   "password123"      HASH      "$2b$12$WvJZq..."
```

*bcrypt* bekerja dengan cara:

- Menghasilkan salt acak secara otomatis (embedded di dalam hash)
- Mengulang proses hashing sebanyak 2¹²= 4096 kali (cost - factor 12)
- Hasilnya berupa string 60 karakter yang sudah mengandung salt dan cost factor
- Password asli tidak pernah disimpan di DB

### 2. Alur Login (POST /api/v1/auth/login)

```
Client                    Server                       Database
  │                          │                              │
  │── email+password ───────▶│                              │
  │   (plaintext HTTPS)      │── SELECT user WHERE          │
  │                          │   email = ? ────────────────▶│
  │                          │◀── user row (hashed_password)│
  │                          │                              │
  │                          │  bcrypt.checkpw(
  │                          │    "password123",
  │                          │    "$2b$12$WvJZq..."
  │                          │  ) → True ✓
  │                          │
  │                          │  Buat JWT Session Token:
  │                          │  Header: {"alg":"HS256"}
  │                          │  Payload: {
  │                          │    "sub": "user-uuid",
  │                          │    "role": "manager",
  │                          │    "iat": now,
  │                          │    "exp": now + 86400s
  │                          │  }
  │                          │  Signature: HMAC-SHA256(
  │                          │    base64(header)+"."+
  │                          │    base64(payload),
  │                          │    JWT_SECRET
  │                          │  )
  │                          │
  │                          │  Buat CSRF Token:
  │                          │  secrets.token_hex(32)
  │                          │  → 64 karakter hex acak
  │                          │
  │◀─ Set-Cookie: session=JWT─│  (HttpOnly, Secure, SameSite=Lax)
  │◀─ Set-Cookie: csrf_token =│  (readable JS, bukan HttpOnly)
  │◀─ Body: {user, csrf_token}│
```

### 3. Alur Request ke Endpoint Terproteksi (GET /api/v1/me)
```
Client                      Server
  │                            │
  │── GET /api/v1/me ─────────▶│  Cookie: session=JWT, csrf_token=X
  │   (Browser otomatis         │
  │    kirim cookie)            │  1. Baca cookie "session"
  │                            │
  │                            │  2. jwt.decode(token, JWT_SECRET):
  │                            │     - Verifikasi SIGNATURE
  │                            │       (HMAC-SHA256 cocok? ✓)
  │                            │     - Verifikasi exp < now?
  │                            │       (belum kedaluwarsa? ✓)
  │                            │     - Extract payload:
  │                            │       {sub, role, iat, exp}
  │                            │
  │                            │  3. Cek role == "manager"? ✓
  │                            │
  │                            │  4. SELECT user WHERE id = sub
  │                            │     (verifikasi user masih aktif di DB)
  │                            │
  │◀── 200 {id, email, role} ──│  role = dari DB (server-derived!)
```

### 4. Alur Proteksi CSRF (POST/PUT/PATCH/DELETE)
```
Client (Browser)               Server
  │                               │
  │  Setelah login, JS membaca    │
  │  cookie csrf_token            │
  │  (bisa dibaca JS krn bukan    │
  │   HttpOnly)                   │
  │                               │
  │── POST /api/v1/... ──────────▶│
  │   Headers:                    │
  │     X-CSRF-Token: <csrf>      │
  │   Cookies (otomatis):         │
  │     session: <JWT>            │
  │     csrf_token: <csrf>        │
  │                               │
  │                               │  hmac.compare_digest(
  │                               │    header["X-CSRF-Token"],
  │                               │    cookie["csrf_token"]
  │                               │  ) → True ✓
  │                               │
  │◀── 200 OK ───────────────────│
  
  
  Jika request dari website lain (CSRF attack):
  
Attacker Site                  Server
  │                               │
  │── POST /api/v1/... ──────────▶│
  │   (Browser kirim cookie       │
  │    session otomatis,          │
  │    tapi TIDAK bisa baca       │
  │    csrf_token dari domain lain│
  │    karena Same-Origin Policy!)│
  │                               │
  │                               │  X-CSRF-Token header: kosong/salah
  │                               │  → hmac.compare_digest gagal
  │◀── 403 Forbidden ────────────│
```

### 5. Alur Sesi Kedaluwarsa
```
Client                      Server
  │                            │
  │── GET /api/v1/me ─────────▶│  Cookie: session=JWT_EXPIRED
  │                            │
  │                            │  jwt.decode():
  │                            │    exp (kemarin) < now → ❌
  │                            │    raise ExpiredSignatureError
  │                            │
  │◀── 401 Unauthorized ───────│  "Session token expired"
  │    (sesi kedaluwarsa,       │
  │     tidak ada data bocor)   │
```

## Komponen Kriptografi yang Digunakan

| Komponen | Algoritma | Fungsi |
| --- | --- | --- |
| Password | bcrypt (cost=12) | Hash satu arah, anti brute-force |
| Session Token | JWT + HMAC-SHA256 | Autentikasi stateless, ada `exp` |
| CSRF Token | `secrets.token_hex(32)` | 256 bit entropi tinggi, kriptografis |
| CSRF Compare | `hmac.compare_digest` | Mencegah timing attack |
| Transport | HTTPS (via `Secure` cookie flag) | Enkripsi seluruh trafik |

Mengapa role tidak boleh dari request body? Role diekstrak dari JWT signature di server — bukan dari klaim client. Jika attacker mengubah payload JWT (misalnya "role":"visitor" → "role":"manager"), signature akan tidak cocok karena mereka tidak tahu JWT_SECRET, dan server menolak token dengan 401.
